# Kickoff — Antigravity 3 · Task BETA1 (closed-beta invite codes in auth-svc)

Design: ADR-034. Contract: `RegisterRequest.invite_code`, `403` `INVITE_REQUIRED` / `INVITE_INVALID` on `register`,
`googleStart?invite_code=`, and the callback redirects in contracts/openapi/auth.v1.yaml. The api-client types were
already regenerated by the architect.

# ROLE
You are Antigravity 3, Node product-services engineer on Winkey (repo luantpbk/winkey). You own services/auth,
services/social, services/realtime, packages/outbox. Never edit contracts/, db/, deploy/, apps/web.

# REPO
Worktree: git worktree add ../winkey-ag3-beta1 -b agent/ag3/beta1-invite-codes origin/main

# TASK (services/auth only; no migration, no new table)
1. Config (config/env.ts, zod):
   - `REGISTRATION_MODE`: `open` | `invite`, default `open`.
   - `INVITE_CODES`: a comma-separated list. Each code matches `^[A-Za-z0-9-]{12,64}$`, with no duplicates.
     Required (at least 1 code) when the mode is `invite`, and ignored when the mode is `open`.
   - Any invalid value → the process refuses to start, and the message never prints a code.
   - At boot, keep only SHA-256 digests of the codes in memory.
2. Helper `checkInvite(code?: string)` → `{ ok: true, index } | { ok: false, reason: 'INVITE_REQUIRED' | 'INVITE_INVALID' }`.
   - Hash the input with SHA-256 and compare it against EVERY digest with `crypto.timingSafeEqual`, without exiting
     early, so the timing does not depend on which code matched.
   - In open mode, always return ok (index null).
3. register:
   - Run the invite check right after body validation and BEFORE any DB lookup. Failure → `403`
     application/problem+json with `code` INVITE_REQUIRED or INVITE_INVALID and a Vietnamese-neutral English `detail`.
   - The existing register rate limit still applies, and failed invites count toward it.
   - On success, log `invite_index` (never the code) in the existing structured "user registered" log line.
4. Google OAuth:
   - googleStart accepts an optional `invite_code` (1–64 chars; otherwise 400). Store it in the signed OAuth cookie
     payload next to state / codeVerifier / returnTo.
   - In the callback, run the check ONLY on the branch that would CREATE a new user. Linking a verified email to an
     existing user, and signing in an already linked Google account, never check the code.
   - Failure → 302 to `/register?error=INVITE_REQUIRED` or `/register?error=INVITE_INVALID`. Create no user, set no
     `wk_rt`, and clear the OAuth cookie as the other error paths do.
5. Metric: `auth_registrations_total{method="password"|"google", result="ok"|"invite_required"|"invite_invalid"}`
   (or extend the existing counter if one exists), so Grafana can show beta sign-ups.
6. `.env.example` and services/auth/README.md: add both variables to the env table. Use a dummy code that is clearly
   fake.

# DEFINITION OF DONE
- Unit tests:
  - config: open default; invite mode with no codes → startup error; a bad code format or a duplicate → startup error;
  - checkInvite: match, mismatch, missing, and a second code in the list matches.
- Integration tests (the existing register/oauth suites, testcontainers):
  - invite mode: missing → 403 INVITE_REQUIRED; wrong → 403 INVITE_INVALID; with a valid code → 201;
  - an already-registered email with a wrong code → 403 INVITE_INVALID, not 409 (no existence leak);
  - open mode ignores invite_code;
  - Google, invite mode: new account without a code → redirect `/register?error=INVITE_REQUIRED` and no user row;
    new account with a valid code → created; an existing linked user signs in without a code;
  - grep the logs captured during the tests: no code value appears.
- The service lint, typecheck and tests pass, root lint + format:check pass, CI is green. Run the new tests 10× in a
  row. The PR is the Handoff Report with real outputs.
- Deploy (Antigravity 2, after merge): the Secret `INVITE_CODES`, then `REGISTRATION_MODE=invite`. You do NOT deploy.
