# Antigravity 3 — SOC-3a: chat-svc (end-to-end encrypted messaging, server side)

Read `AGENTS.md`, then **ADR-049** section 5 and the SOC-3 addendum (2026-10-30) at the end of `docs/DECISIONS.md`, then `contracts/openapi/chat.v1.yaml` in full (its `info` description holds the rules), the `chat.hint` part of `contracts/realtime/README.md` and `server.schema.json` (`chatHint`), and migration `000033_chat_e2ee` (merged; do not write migrations).

Create the new service `services/chat` (Node 22, Fastify, kysely, pino: the same stack and layout as `services/social`). Branch `agent/ag3/soc3a-chat-svc` from `origin/main`. If the PR gets large, split it: (1) devices, keys and to-device; (2) conversations and messages; (3) realtime hints, rate limits and the purge job. Each part must pass CI on its own. Do not merge your own PR.

**The server never decrypts anything.** It must also never log ciphertext, keys or signatures. Log ids and sizes only.

## 1. Service basics
- `/healthz`, `/readyz` (db, valkey, nats), JSON logs, env config with `.env.example`, a README (endpoints, env table, run/test), and a Dockerfile (multi-arch). AG2 wires the deployment.
- Identity only from `X-User-Id` / `X-User-Roles`. Every endpoint requires a user (`401` otherwise).
- Profiles from `auth.public_profiles`, blocks from `social.blocks`, follows from `social.subscriptions` (read-only grants, AG2).

## 2. Devices and keys
- Verify ed25519 signatures with Node `crypto.verify(null, msg, publicKey, sig)`. Build the public key from the 32 raw bytes (DER SPKI prefix `302a300506032b6570032100`). The canonical JSON is in the contract: keys sorted, no whitespace. Write a helper with unit tests against vectors produced by vodozemac. Ask AG1 for a fixture of three signed device-key and one-time-key objects generated by the spike wrapper; commit them as test fixtures.
- `putMyDevice`:
  - in one transaction, take a per-user advisory lock (`pg_advisory_xact_lock(hashtext('chat-dev:'||user_id))`) to count active devices (max 10);
  - insert or update; map `23505` on `devices_curve25519` to `409 IDENTITY_KEY_IN_USE`;
  - a different user's or a removed `device_id` → `409 DEVICE_ID_IN_USE`.
- `claimKeys`: per device, `DELETE FROM chat.one_time_keys WHERE (device_id, key_id) = (SELECT device_id, key_id … WHERE device_id = $1 ORDER BY created_at, key_id LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING …`, else the fallback key. Batch the whole request in one round trip if you can (CTE over `unnest($ids)`), and exclude devices whose owner is in a block relation with the caller.
- `queryDevices`: one query for all users, with block and profile filters.
- After registration or removal, send `chat.hint` `DEVICES {user_id}` to every user sharing an `ACTIVE`/`REQUESTED` conversation with the caller (one query for the distinct user ids).

## 3. To-device
- Accept a recipient device only if: it is one of the caller's own active devices, or its owner shares a conversation with the caller where both memberships are `ACTIVE`/`REQUESTED`, and there is no block either way. Compute this in one query for the batch. Skip the others and list them.
- Insert in one statement (`INSERT … SELECT FROM unnest(...)`), then send one `chat.hint` `TO_DEVICE` per distinct recipient user.
- `listToDevice`: own device only (`404` otherwise). `id > after`, ordered by `id`, `limit + 1` to compute `has_more`. Update `last_seen_at` at most once a minute.
- `ackToDevice`: `DELETE … WHERE recipient_device_id = $1 AND id <= $2`.
- **Purge job** (in process, every hour, Valkey lock so only one replica runs it): delete to-device rows older than 30 days in batches of 5 000.

## 4. Conversations
- Rules are in the contract (`createConversation`, `addMembers`, `removeMember`, `acceptConversation`, `updateMember`). Implement them in transactions that lock the conversation row (`SELECT … FOR UPDATE`), so `last_seq`, member counts and owner hand-over are consistent.
- `DIRECT` uniqueness: `direct_key` = the two user ids sorted, joined with `:`. Insert with `ON CONFLICT (direct_key) WHERE direct_key IS NOT NULL DO NOTHING`, then read the existing row.
- `REQUESTED` vs `ACTIVE`: `EXISTS (SELECT 1 FROM social.subscriptions WHERE subscriber_id = <added user> AND channel_id = <actor>)`.
- **SYSTEM messages:** every membership or title change inserts one with the next `seq` (same transaction, `UPDATE chat.conversations SET last_seq = last_seq + 1 … RETURNING last_seq`), with the `system_body` shapes in the contract.
- `Conversation` building, for a page: members (`ACTIVE` + `REQUESTED`) with profiles in one query, and `unread_count` computed in SQL (`count(*)` over messages with `seq > greatest(last_read_seq, joined_seq - 1)` and `sender_id IS DISTINCT FROM caller`, capped at 99 via `LIMIT 100`).
- `listConversations`: keyset on `(coalesce(last_message_at, created_at) DESC, id DESC)`, using the opaque cursor helper you already have in social-svc. Add an index only if EXPLAIN shows a need. If so, ask the architect for a migration; do not write one.

## 5. Messages
- `sendMessage`: checks in this order: membership (`LEFT` or none → `404`; `REQUESTED` → `403 REQUEST_PENDING`), device ownership, DIRECT closed or blocked. Idempotency via `messages_idempotency` (`23505` → return the stored message with `200`). Assign `seq` by `UPDATE … SET last_seq = last_seq + 1, last_message_at = now() RETURNING last_seq` in the same transaction. Then send `chat.hint` `MESSAGE {conversation_id, seq}` to every `ACTIVE`/`REQUESTED` member, after the commit.
- `listMessages`: the readable range `[joined_seq, left_seq ?? last_seq]`, three modes (after, before, newest), `limit + 1` → `has_more`.
- `deleteMessage`: own `ENCRYPTED` message only → `ciphertext = NULL, deleted_at = now()`. Idempotent.

## 6. Realtime hints and rate limits
- Publish hints after commit with core NATS `nc.publish('rt.chat.user.' + userId, JSON)`, payload exactly the `chatHint` object. Never put them in an outbox or JetStream. A publish failure is logged and ignored (hints are at-most-once).
- Rate limits (Valkey, the existing limiter): the numbers in the contract `info`, `429` with `Retry-After`.

## 7. Tests (Definition of Done)
- Unit: canonical JSON and signature verification (valid, tampered, wrong key), the REQUESTED/ACTIVE decision, cursor encoding.
- Contract tests: every response validated against `chat.v1.yaml` (copy the pattern in `services/social/tests/contracts`).
- Real-PG integration:
  - **claims:** 20 concurrent claims on a device with 10 keys → 10 distinct keys, then fallback;
  - **device limits:** an 11th device → `409`; reused identity key → `409`; changed keys for an existing id → `409`;
  - **to-device:** recipient filtering (stranger, blocked, shared conversation, own device), ack, purge;
  - **conversations:** DIRECT uniqueness under 10 concurrent creates; REQUESTED vs ACTIVE; accept and decline; block → `403`; 51st member → `409`; owner leaving hands over; history range for a member added later and after leaving;
  - **messages:** `seq` contiguous under 50 concurrent sends; idempotent retry; delete tombstone.
- No secrets, keys or ciphertext in logs (add a test that captures logs during a send and asserts that the ciphertext substring is absent).
